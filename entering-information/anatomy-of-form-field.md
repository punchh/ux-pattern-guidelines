# Anatomy of form field

{% hint style="success" icon="sparkles" %}
[**Get the AI skill**](anatomy-of-form-field.md#ai-skill-file) for this UX pattern guideline in a markdown (.MD) file.
{% endhint %}

<figure><img src="../.gitbook/assets/image (95).png" alt=""><figcaption><p>The collection of atomic elements that compose a form field. Some common to all field types (description, tooltip, required indicator, and error message), and some input region elements unique to text fields, dropdown lists, and combo boxes.</p></figcaption></figure>

Even when we can offer users a wide range of techniques and formats for entering information, it's important that all field types follow the same information architecture and hierarchy of supporting elements - each used in a predictable way each time.

### Description text

<figure><img src="../.gitbook/assets/image (87).png" alt=""><figcaption></figcaption></figure>

Just below the label, the description is a succinct instruction for _how_ to fill out the field, or conveying must-know implications that affect trust or decision making. Always very, very concise.

### Tooltip

<figure><img src="../.gitbook/assets/image (85).png" alt=""><figcaption></figcaption></figure>

Accessed on hover through an icon just after the field label, a [tooltip](../reading-information/tooltips.md) explains the "why" or context for the field

### Required field indicator

<figure><img src="../.gitbook/assets/image (86).png" alt=""><figcaption></figcaption></figure>

To signal needing to be filled to submit the form. Read more about r[equired field patterns](../form-experience/required-versus-optional-fields.md).

### Input region

<figure><img src="../.gitbook/assets/image (94).png" alt=""><figcaption></figcaption></figure>

The width of the input region on a text or numeric field should reflect the typical input value length. This helps users anticipate the type of value that they’ll enter.

For example, when entering a percentage, the input region shouldn't be wider than what's needed to accommodate 3 numeric characters.

It should _not_ span the width of the entire screen or body for the sake of filling the screen or section, nor for purely aesthetic symmetry.

### Syntax icon

<figure><img src="../.gitbook/assets/image (88).png" alt=""><figcaption></figcaption></figure>

Conveys expected format or type of information. Always left aligned. Not all fields need to have this, but it’s a nice to have if can be represented using a familiar icon. Usually _not_ interactive.

### Hint text

<figure><img src="../.gitbook/assets/image (89).png" alt=""><figcaption></figcaption></figure>

Shows a sample input value, or the syntax/format

### Clear button

<figure><img src="../.gitbook/assets/image (91).png" alt=""><figcaption></figcaption></figure>

Appears only when a value is populated. Clears the value. Usually only for combo box and search fields.

### Right-most icon

<figure><img src="../.gitbook/assets/image (92).png" alt=""><figcaption></figcaption></figure>

This is usually an interactive icon button, most common in dropdown lists and combo boxes as a chevron to toggle the dropdown list visibility. Another common example is the unmask/mask password icon button in a password field.

### Error validation message

<figure><img src="../.gitbook/assets/image (93).png" alt=""><figcaption></figcaption></figure>

Always bottom-aligned with respect to the input region. Learn more about [error validation patterns](../form-experience/error-validation.md).
